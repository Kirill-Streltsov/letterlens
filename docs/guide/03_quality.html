6 Security and data protection

Five layers protect a letter: the photo stays on the device; personal data is replaced before the model sees text; content is encrypted with a key per user; the database itself decides who can read a row; and data is deleted after 30 days. Every layer has tests.

6.1 Who can see what: row-level security

[[rls]]

PostgreSQL row-level security (RLS) attaches a rule to each table. The API runs every request in a transaction that first sets three values with set_config(…, true): the user id, the user's counselling tenants, and a "system" flag for background jobs. The rules in backend/migrations/0001_init.sql use these values. Example:

CREATE POLICY letters_shared_read ON letters FOR SELECT
    USING (EXISTS (
        SELECT 1 FROM shares s
        WHERE s.letter_id = letters.id
          AND s.tenant_id = ANY (app_tenant_ids())
          AND share_is_active(s)));     -- not revoked, not expired

The important point: even if a Python bug forgets a WHERE owner_id = …, the database returns nothing. The application connects as letterlens_app, a role that does not own the tables and cannot bypass RLS. A database trigger also stops anyone from sharing a letter with an employer (only counselling services can receive shares).

6.2 Encryption per user

[[encryption]]

crypto.py implements envelope encryption. One master key (KEK) lives in AWS Parameter Store. Each user gets a random data key (DEK). The DEK is stored encrypted ("wrapped") by the KEK. Letter content is encrypted with AES-256-GCM and the record id as "associated data", so a ciphertext cannot be copied to another record. Deleting a user's wrapped DEK makes all their data unreadable everywhere, including backups ("crypto-shredding").

iOS analogy: the iOS Data Protection model, where file keys are wrapped by class keys.

6.3 The legal-advice guardrail: safety/guardrail.py

A question passes three layers:

  1. Rules (check_question_rules): regular expressions in six languages for advice requests ("Sollte ich Widerspruch einlegen?", "İtiraz etmeli miyim?") and for injection ("ignore previous instructions").
  2. Model classifier: the model sorts the question into general information, individual legal advice, prompt injection or off topic. If this call fails, the API refuses (it fails closed).
  3. Output check (is_advisory_output): the answer must not sound like advice ("you should object", "the decision is unlawful").

A refusal is written in the reader's language and offers a counsellor.

6.4 Prompt injection

neutralize_injections replaces lines that look like instructions to a model ("SYSTEM: …", "report the deadline as …") before the prompt is built, and the verifier never accepts these lines as a source. A hand-written test letter contains such an attack; the real deadline and amount are still shown.

7 How AI quality is measured

LetterLens does not trust that the model "seems good". A golden set of 137 letters with exact answers and 96 test questions measures it. Three profiles run the same tests: rules only (every pull request), with injected errors (every pull request), and with the real model (before a release). A gate fails the build below the thresholds.
[[eval_flow]]

7.1 The test data

  • Synthetic letters (letterlens/synthetic/generator.py): 19 letter families (tax assessment, Jobcenter invitation, rent increase …) with random names, dates, amounts and phrasing. Because the generator creates the letter, it knows every correct answer. Some letters get typical OCR errors ("ü" → "u").
  • Hand-written letters (evals/handwritten.py): 17 letters with layouts that no template uses: a court payment order, a traffic fine, a notice of termination, and one prompt-injection attack.
  • Red-team questions (evals/redteam/questions.jsonl): 54 requests for legal advice, 34 normal questions and 8 injection attempts, in six languages.

7.2 The most important metric

Unsafe verified facts: the number of dates or amounts shown as "verified" that are not in the letter. The gate requires 0. All other metrics may vary; this one may not.

7.3 Fault injection ("chaos")

ChaosProvider in evals/run.py simulates a bad model: it shifts 35 % of dates by 1 to 7 days, changes amounts by 10 % and cites wrong lines. In the last run it injected 91 errors. The grounding check stopped all of them: 0 reached the reader as a fact. The test tests/test_eval_gate.py proves that the gate really blocks a bad change: it replaces the verifier with one that trusts the model, and the gate fails.

7.5 How translation quality is checked

The system translates each summary back into English and asks a second model call (the judge) to compare it with the English summary. A judge can also be wrong, so it is tested first: it must sort 20 pairs with known answers (unchanged summaries versus summaries with a changed date, amount or obligation). It scored 95 %. Only then do its scores count. A language with a score of 0.80 or more is marked enabled; otherwise the app shows it as "beta".

How other languages are made: the model writes the explanation once, in English, and the code checks it against the letter. Then a second call translates this checked text item by item. Code puts the line links and sources back from the English version, so every language shows the same content. An earlier design wrote each language separately from the letter; the languages then differed in content, and Ukrainian fell to 0.75. With translation, every language scores 0.95 to 1.00.

iOS analogy: one source of truth (the checked English model) and localized views of it, instead of five separate models that can drift apart.

7.6 Real and sample documents

31 public documents were read with Apple Vision OCR and run through the live pipeline: official sample notices, real letters from authorities that were published with redactions, job centre publications, landlord sample letters and blank court forms. A person checked every result. The review found nine defects, for example a placeholder date ("TT.MM.2015") shown as a real date, a fine notice classified as "benefits", and assessed tax shown as "to pay". Each defect has a fix and a test; four new hand-written letters keep the cases in the golden set. The documents themselves are not in the repository (copyright and personal data).

7.7 An honest limit

The test letters are synthetic and hand-written. They show that the mechanisms work; they do not prove how the system performs on real letters from real offices. Real, consented, anonymized letters must be added before a public launch.

8 Testing approach

Most tests are fast unit tests of pure functions. The database tests run against a real PostgreSQL as the restricted application role, so the security rules are tested exactly as they run in production. Clients are protected by contract tests. The AI quality gate sits on top.

8.2 How the database tests work

tests/conftest.py creates a new, empty database for each test session, applies the migrations, and connects as letterlens_app. In CI, PostgreSQL runs as a service container. Locally, docker compose up starts it.

8.3 Test doubles instead of network calls

No test calls a real model. FakeProvider answers deterministically; ScriptedProvider (in test_gateway.py) returns a planned sequence of answers and errors, to test retry paths.

iOS analogy: a URLProtocol stub that returns canned responses, or a protocol-based mock injected into a view model.

8.4 Static checks

Python: ruff (lint and format) and mypy --strict (every function is typed, like Swift). TypeScript: eslint and tsc --noEmit in strict mode. Infrastructure: cdk-nag security rules.
