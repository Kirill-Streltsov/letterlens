4 Architecture

Two clients (iOS and web) read the letter on the device and send only text. One API on AWS Lambda stores the letter encrypted and starts a background workflow. The workflow uses a small local model, the Mistral language model and plain code. PostgreSQL stores all data and decides who can see what.
[[big_picture]]

4.1 Five constraints

Five constraints decide the design. Each constraint has a direct effect.

ConstraintEffect on the design
A wrong deadline can harm a reader.The model proposes facts. Code verifies them. A value that is not verified shows as "please check".
A legal assessment of an individual case is a regulated legal service (§ 2 RDG).The product explains. A guardrail refuses individual advice and offers a counsellor.
Letters are among the most sensitive documents that people have.OCR on the device, pseudonymization before the model, encryption per user, 30-day retention, processing in the EU.
The hosting budget is 0 €.Serverless services with "always free" limits, a free PostgreSQL, an EU model provider with prepaid credit. Paid upgrades are documented, not necessary.
One engineer builds and operates it.A modular monolith: one Python package, one database, one deploy.

4.3 Why "a modular monolith on serverless"

The backend is one Python package with clear modules. It runs as Lambda functions. There are no microservices. One engineer operates the product, and one database and one deploy are easier to understand and to test. A serverless function costs nothing when nobody uses it. This keeps the hosting inside the free limits.

iOS analogy: one app target with well-separated Swift packages, instead of several apps that talk to each other.

The same pipeline steps run in two ways. In production, AWS Step Functions calls each step in a separate Lambda call. In tests and local development, one Python process calls all steps. The steps do not know the difference.

6 The life of one letter

The upload returns at once. A background workflow then runs the pipeline steps. The app asks for the status every 1.5 seconds until the status is "ready". Only three steps call the language model; the other steps are plain code.
[[life_of_letter]]

6.1 Step by step

  1. On the phone. VisionKit finds the page edges. Apple Vision reads the German text. DocumentBuilder.build (Swift) sorts the lines from top to bottom and gives each line a number, for example p1-l13 = page 1, line 13. These ids are the base of the grounding check.
  2. Upload. The app sends POST /v1/letters with the lines and an Idempotency-Key. If the network sends the request two times, the server returns the first answer. It does not make a second letter.
  3. Accept. LetterService.create checks the rate limit (30 per minute) and the monthly quota (3 letters on the free plan). Then it encrypts the letter with the key of the reader and stores it.
  4. Start. The API starts a Step Functions execution and answers 202 Accepted at once.
  5. Pipeline. The steps run in the worker Lambda (figure 3). After each step, the worker saves the state encrypted.
  6. Ready. The status Lambda sets the status to ready. The app shows the result.
[[pipeline]]

6.2 What happens when something fails

FailureResponse
The model times out or is rate-limitedThe gateway tries 3 times with longer pauses. Then it tries the fallback model.
All models fail, or the monthly budget is spentA rule-based extractor and a template explanation take over. The letter is marked degraded, and the app shows a warning.
A pipeline step crashesStep Functions tries the step two more times. Then the letter gets the status failed, and the reader can send it again.
The model returns broken JSONThe gateway asks one more time and sends the error message ("repair"). Then it uses the fallback.
A translation has a missing or an extra itemThe step writes the explanation directly in the target language.

7 The AI pipeline in detail

Each step is a pure function: it reads the state, does one task, and writes the state. The model writes only three things: the facts with their line ids, the English explanation, and the translations. Code checks each of them before the reader sees them.

7.1 Input

The client sends a LetterDocument: text lines with page, index, an optional bounding box and the OCR confidence. Each line has the id p{page}-l{index}. All facts and all summary sentences refer to these ids.

7.2 Classify

A TF-IDF model with logistic regression gives the letter type: tax, benefits, health_insurance, immigration, landlord or other. Below a probability of 0.5, it abstains, and the type is other. The type selects the guidance paragraph in the extraction prompt and filters the retrieval.

7.3 Extract

  1. Remove lines that look like instructions to a model (neutralize_injections).
  2. Replace personal data with placeholders (PiiVault, chapter 8.5). The model sees [TAXNO_1], not the tax number.
  3. Call the gateway with the task extract, the prompt extract-v5 and the strict schema Extraction.
  4. Put the original values back into the result (PiiVault.restore).
  5. If the gateway fails, use the rule-based extractor (extraction/rules.py) and mark the letter degraded.

7.4 Verify

The verifier sets the trust state of each fact. Chapter 8.3 shows the code.

SituationStateNote for the reader
The cited line contains the date or the amountverifiednone
The value is in a different lineneeds_check"appears in the letter, but not in the quoted line"
The date is nowhere in the letterneeds_check, no date"no date for it was found in the letter". If the cited line names a period, code estimates the date with the rule.
The amount is nowhere in the letterremovedThe reader never sees it (for example a blank field "_ EUR" read as 0.00)
A date before the letter dateneeds_check"before the letter date"
A relative period ("within one month")needs_check, estimatedThe rule, for example "1 month; received on …"

7.5 Retrieve

The query contains the subject, the sender, the deadline and action texts, and the first 2,500 characters of the letter. German terms such as "Widerspruch" carry most of the signal. The retriever ranks the passages with BM25 and optional embeddings, fuses both rankings, filters by type, and returns up to 4 passages c1 … c4.

7.6 Explain

The model writes in English (prompt explain-v6): a headline, the kind of letter, 3 to 10 summary sentences with line ids, 1 to 4 "next steps" with passage ids, and short labels for each deadline and amount. The prompt tells the model to cover five points: the decision, the conditions, the consequences, the actions and the permissions. A signed receipt form is always a required action.

7.7 Sanitize

RuleAction
A sentence sounds like individual legal adviceRemove it
A sentence contains a number that is not in the letter or in the verified factsRemove it
A next step has no valid passage idRemove it
A line id does not existRemove the id
A URLRemove it

The log records only the counts of removed items (explanation sanitized), never the text.

7.8 Translate

[[translation]]

The other languages translate the checked English explanation (prompt translate-explanation-v1). The model returns each summary sentence and each next step with its index, and each label with its fact id. Code puts the line ids, the passage ids and the citations back from the English source. Before the call, PiiVault.reapply hides the names again with the same placeholders.

Why this design? Before, the model wrote each language directly from the letter. The languages then differed in content, and the faithfulness score of Ukrainian fell to 0.75. With translation, all languages score 0.95 to 0.975, and 100 % of the translations keep one sentence for each English sentence.

iOS analogy: one source of truth (the checked English model) and localized views of it, instead of five separate models that can drift apart.

7.9 Questions about a letter

POST /v1/letters/{id}/questions runs three layers. First, rules in six languages find advice requests and injection. Second, a model call (task guard) sorts the question into general information, individual legal advice, prompt injection or off topic. If this call fails, the API refuses (it fails closed). Third, the model answers (task answer), and code checks the answer for advice phrases and for numbers that are not in the letter.
